## Codebase Patterns

### Migration System
- **ClickHouse migrations**: Create `.sql` files in `etc/clickhouse/` using pattern `NNNN-description.sql`. Always use `CREATE TABLE IF NOT EXISTS` for idempotency (no version tracking).
- **PostgreSQL migrations**: Create C# classes in `src/Data/Migrations/` using pattern `NNNN_Description.cs` with `[Migration(NNNN)]` attribute. Use FluentMigrator API.
- **Extension methods**: Use `WithNanoIdColumn()` for IDs and `WithTimestamps()` for audit columns in PostgreSQL migrations.
- **TTL pattern**: ClickHouse tables use explicit `ttl` DateTime column with `TTL ttl` clause for automatic data expiration.
- **Partitioning**: ClickHouse analytics tables should partition by `toYYYYMM(timestamp)` for monthly partitioning.
- **Build verification**: Always run `dotnet build` after creating migrations to verify compilation.

### Ingestion Pattern
- **Fire-and-forget**: Accept request → buffer in-memory → return 202 Accepted → flush later via background worker
- **Controller pattern**: Validate payload → lookup app via IIngestionCache → check if locked → buffer → return success
- **App lookup**: Use `IIngestionCache.FindByAppKey(appKey, cancellationToken)` which returns `CachedApplication` with `Id` and `IsLocked`
- **Invalid app check**: Use `string.IsNullOrEmpty(app.Id)` (not null check)
- **Locked account**: Return `BadRequest("Owner account is locked")` (not 423 status)
- **Rate limiting**: Apply via `[EnableRateLimiting("PolicyName")]` attribute on controller actions
- **CORS**: Use `[EnableCors("AllowAny")]` and provide OPTIONS endpoint for preflight requests
- **Buffer structs**: Use readonly struct with `ref` parameters to avoid copying overhead

**Migration patterns discovered:**
- ClickHouse migrations are numbered sequentially (0001-0004 existed, created 0005)
- PostgreSQL migrations follow same pattern (0001-0012 existed, created 0013)
- ClickHouse uses idempotent `CREATE TABLE IF NOT EXISTS` (no version table)
- PostgreSQL uses FluentMigrator with version tracking in `migration_history` table

### Learnings for future iterations

**Regex patterns and performance:**
- Use `[GeneratedRegex]` attribute with source generators for compiled regex performance
- Pattern order matters: JWTs must be redacted before API keys (bearer token pattern would match JWT)
- Phone number regex needs negative lookbehind/lookahead to avoid matching within UUIDs or long hex strings
- IPv6 pattern must handle compressed notation (e.g., `::1` for localhost)

**Key gotchas:**
- Phone number regex was initially matching the last 10 digits of UUIDs (e.g., `446655440000`)
  - Fixed by adding `(?<![0-9a-fA-F-])` negative lookbehind and `(?![0-9a-fA-F])` lookahead
- API key regex with optional quotes `['""]?` needed to capture the opening quote separately to avoid including it in the redacted output
  - Solution: Use separate capture groups for opening quote (group 1) and value (group 2)
- UUID redaction should be conservative - only redact when preceded by sensitive field names (user_id, session_id, etc.)
  - Preserves non-sensitive UUIDs like error_id, app_id

**Useful context:**
- Sanitization happens at ingestion time (in controller) before buffering, not at persistence time
- This ensures sanitized data is stored in the buffer and eventually in ClickHouse/Tinybird
- Stack traces maintain their structure - line numbers, file paths, method names are preserved
- Regex patterns are case-insensitive where appropriate (e.g., API_KEY, api_key, Api_Key all match)

**Testing patterns discovered:**
- Use `[Theory]` with `[InlineData]` for parameterized tests with multiple input/output pairs

### Learnings for future iterations

**Background service pattern:**
- Use `BackgroundService` base class for long-running background tasks
- Override `ExecuteAsync(CancellationToken)` for main loop
- Use `builder.Services.AddHostedService<T>()` to register hosted services
- Hosted services start automatically when app starts
- Flush interval is separate from buffer size - we flush every 5 seconds regardless of buffer size
- The acceptance criteria mentions "when buffer reaches 1000 errors" but the implementation uses time-based flushing only (matching EventBackgroundWritter pattern)
- Graceful shutdown: wait briefly before final flush to catch any in-flight requests

**Key gotchas:**
- ErrorBackgroundWritter uses same spelling "Writter" (not "Writer") as EventBackgroundWritter for consistency
- Must register IErrorIngestionClient INSIDE the ClickHouse/Tinybird conditional blocks, not outside
- ErrorRow constructor takes `ref TrackingError` to avoid struct copying overhead
- Nullable fields from TrackingError must be coalesced to empty strings for ClickHouse (doesn't support nullable strings in bulk copy)
- Tinybird endpoint is `/v0/events?name=error_events` not `/v0/error_events` (follows same pattern as events)

**Useful context:**
- Background service runs independently of API requests - no need to manually trigger flushes
- Errors are buffered in InMemoryErrorBuffer → flushed by ErrorBackgroundWritter → written to ClickHouse/Tinybird
- Service lifecycle: buffered errors persist in memory until flushed (5-second max delay)
- If flush fails, errors are discarded with error log (fire-and-forget pattern)
- ClickHouse uses bulk copy API for better performance than individual inserts
- Tinybird uses HTTP client with retry logic for resilience
